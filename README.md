# Stugora

Lists cottages across the Nordics and the Baltics (Finland, Sweden, Norway,
Denmark, Iceland, Estonia, Latvia, Lithuania) on Airbnb, Booking.com and Vrbo
for their owners.
Pricing (plan of 28 Oct 2026): €99 a year per cottage plus 12% of the owner's
payout on bookings from Stugora's channels, both plus 25.5% VAT. Nettimökki
bookings are never charged. Pilot owners pay 10% and their first year is free.

## What is here

- `backend/` — Django 5.2 + Django REST Framework
  - `owners` app: `OwnerSignup` (the stugora.fi form), `Owner`, `Cottage` (intake),
    `Booking` (commission and VAT per stay, yearly fee per listing year)
  - `POST /api/signups/` — public, throttled (10/hour per IP), honeypot field, emails the team
  - owner dashboard API, signed in with a six-digit code emailed to the owner
    (no passwords; 15 minutes, 5 tries, at most 5 codes an hour):
    `POST /api/auth/request-code/`, `POST /api/auth/verify-code/`, `POST /api/auth/logout/`,
    `GET /api/owner/summary/?year=`, `GET /api/owner/bookings/?year=`
  - messages between guests and owners: `POST /api/enquiries/` (from a cottage page; throttled,
    honeypot) starts a conversation and returns its private token; the guest reads and
    replies at `/api/conversations/<token>/` (no account; the link is emailed to them and the
    owner never sees their email). Owners use `/api/owner/conversations/` and
    `/api/owner/conversations/<id>/` (read, reply, archive). Owner and guest are emailed in
    their own language when a message arrives. Threads from Airbnb, Booking.com and the
    other sites will come in through the channel manager; until then they are demo data and
    replies to them stay in Stugora. Enquiries about example cottages with no owner go to
    `SIGNUP_NOTIFY_EMAILS` and are answered in the admin
  - AI reply suggestions: `POST /api/owner/conversations/<id>/draft/` sends the conversation, the
    cottage's facts (amenities, house rules, booked dates) and the owner's optional notes or own
    draft to Claude (`owners/assistant.py`) and returns a suggested reply for the owner to edit and
    send; nothing is sent to the guest from there. Needs `ANTHROPIC_API_KEY` (in `backend/.env`
    locally; see `backend/.env.example`). Guests' messages go to Anthropic for this, so the
    privacy policy must name Anthropic as a processor
  - listings (Hosting → My listings, `owners/listings.py`): `GET/POST /api/owner/cottages/`,
    `GET/PATCH/DELETE /api/owner/cottages/<id>/`, `…/status/` (publish, pause, relist, archive, restore),
    `…/duplicate/`, `…/preview/` (no address, door codes or arrival notes; location rounded to about
    1 km unless the owner shows it exactly), photos `…/photos/`, `…/photos/<pid>/`, `…/photos/<pid>/replace/`,
    `…/photos/order/`. Every view looks the cottage up among the signed-in owner's own (404 otherwise).
    Delete only works for a cottage with no stays and no guest messages; archive waits until no stays are
    coming. Each change is logged in `CottageChange` (shown in the admin). These change Stugora's own
    listing only: Airbnb, Booking.com, Vrbo and Nettimökki keep theirs, and a calendar link (iCal)
    carries dates, never texts, photos or prices
  - `python manage.py seed_demo` — a demo owner (demo@stugora.fi) with three cottages and a
    year of bookings; `./dev.sh` creates it on a fresh database
  - `/admin/` — work the sign-ups, owners, cottages and bookings
- `frontend/` — Next.js 16 site for stugora.fi, in ten languages
  - every page lives under its language: `/en`, `/fi`, `/sv`, `/nb`, `/nn`, `/da`, `/is`,
    `/et`, `/lv`, `/lt`, e.g. `/sv/hosts` and `/et/cottages/lakeside-villa`; `/` and any
    address without a language redirect to the visitor's saved or browser language
    (`src/proxy.ts`), and the old Finnish addresses `/mokit/…` and `/omistajille` redirect
  - guest homepage `/<lang>`: search, categories, filters, saved cottages,
    Country → Region → Town pickers and a map view (Leaflet + OpenStreetMap tiles);
    search, dates and guests are kept in the address, so a change of language keeps them;
    example cottages in `src/lib/listings.ts`
  - owner page `/<lang>/hosts`: earnings estimator and sign-up form
  - `src/lib/places.ts`: 98 regions and their towns with coordinates, generated by
    `scripts/build-places.js` from GeoNames (CC BY 4.0). To change it, in a normal terminal:
    `cd ~/stugora/scripts && npm install && node build-places.js`
  - My listings `/<lang>/hosting/listings`, the editor `/<lang>/hosting/listings/<id>` (sections in the
    address hash: `#basics`, `#photos`, `#amenities`, `#pricing`, `#rules`, `#arrival`, `#location`,
    `#calendar`, `#status`) and the owner-only preview `/<lang>/hosting/listings/<id>/preview`. Photos are
    resized in the browser to at most 2560 px before upload (`src/lib/imagePrep.ts`); unsaved edits are
    kept in the browser until saved. Amenity keys: `src/lib/amenities.ts` (keep in step with the backend)
  - owner dashboard `/<lang>/hosting` (sign in at `/<lang>/hosting/login`; `/hallinta`
    redirects to `/fi/hosting`): stays now and coming up, earnings, Stugora's share, earnings
    by month, sites, cottages, the year's bookings with CSV download, yearly fees; words in
    the `dashboard` part of the messages files. Messages at `/<lang>/hosting/messages`;
    guests write from the cottage page ("Message the owner") and continue at
    `/<lang>/messages/<token>`. The browser reaches Django through the
    site's own `/api/*` path (`next.config.ts`), so the sign-in cookie is first-party.

- `mobile/` — the iPhone and Android app (Expo), travelling and hosting in one app; see
  `mobile/README.md`. It signs owners in with the same emailed code and then a per-phone
  key (`Authorization: Bearer`, `owners/app.py`); `POST /api/owner/device/` registers the
  phone for push notifications about new bookings, messages and booking requests, and
  `PATCH /api/owner/me/` sets the owner's language. Signed-in phones are listed in the admin
  under App devices.

## Calendar and booking link

Each cottage has one calendar, the master (Hosting › Calendar, `/<lang>/hosting/calendar`):

- **What fills it:** bookings from every site, dates read from Airbnb, Booking.com and Vrbo
  through their calendar links (iCal, read every 15 minutes by `manage.py sync_calendars`),
  Nettimökki bookings from forwarded emails, and dates the owner closes. Overlaps between
  different sites are shown as double bookings.
- **What the sites read back:** `/api/calendar/<token>.ics?site=airbnb` (one link per site,
  leaving out that site's own bookings). It says only "Not available", never guest names.
- **Booking link:** `/book/<token>`, for the owner's own guests. A guest picks free dates and
  sends a request; it lands in the owner's calendar and inbox. Accepting it books the stay as
  the owner's own booking (never charged) and closes the dates everywhere. The owner takes
  the payment as before; Stugora handles no money. The owner can stop requests or make a new
  link if the old one spread too far.

Code: `backend/owners/calendar.py`, `booking_requests.py`, `calendar_views.py`;
`frontend/src/components/owner/OwnerCalendar.tsx`, `components/BookingRequest.tsx`.

## Languages

All the words are in `frontend/src/i18n/messages/<lang>.ts`; English (`en.ts`) is the
source and the fallback for anything a language is missing. How to translate:
`frontend/src/i18n/TRANSLATING.md`. Adding a language: its code in
`src/i18n/locales.ts`, one messages file, and the code in the backend's `Language`
choices; routes, the language picker, hreflang and sitemaps follow.

Numbers, prices, dates, plural forms and country names come from the browser's own
locale data (`Intl`), so they are right for every language without translating them.

Checks, in a normal terminal:

```bash
cd ~/stugora/frontend
npm run i18n:check     # lists missing keys, plural forms, list lengths, {placeholders}
npm run test:i18n      # localization tests
```

The non-English text is machine-written and should be read by a native speaker before
launch, Icelandic, Latvian, Lithuanian and Nynorsk first.

## Run it locally

In a normal terminal:

```bash
cd ~/stugora
./dev.sh
```

The first run sets up a Python virtual environment and installs the npm
packages, which takes a few minutes. It then opens http://localhost:3100.

| What | Address |
| --- | --- |
| Guest site | http://localhost:3100 (redirects to /en, /fi, /sv …) |
| Owner sign-up page | http://localhost:3100/en/hosts, /fi/hosts … |
| Owner dashboard (sign in as demo@stugora.fi; the code shows on the page) | http://localhost:3100/fi/hosting, /en/hosting … |
| Admin (sign-ups, owners, bookings) | http://localhost:8100/admin |

Ports 3100 and 8100 leave 3000 and 8000 free for Bona. Press Ctrl+C to stop.
To log in to the admin, in a normal terminal:

```bash
cd ~/stugora && backend/.venv/bin/python backend/manage.py createsuperuser
```

Tests, in a normal terminal:

```bash
cd ~/stugora/backend && .venv/bin/python manage.py test
```

## Before the page goes public

- Switch map tiles from tile.openstreetmap.org (fine for development only) to a
  hosted tile provider such as MapTiler or Stadia Maps
- Move the "Nearby" lookups (frontend/src/lib/nearby.ts) behind a small Django
  endpoint that caches Wikipedia's answer per cottage for a week, so each page
  view doesn't call Wikipedia from the guest's browser
- Buy stugora.fi and set up hello@stugora.fi (used on the page)
- Privacy policy page (GDPR), naming Anthropic as processor for AI reply suggestions, and a link to it next to the consent box
- Finnish copy checked by a native speaker
- Confirm with the accountant that Elda-Auto Tmi charges VAT on Stugora fees
